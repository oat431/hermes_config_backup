## Em-dash removal convention (user-approved: context-aware)

Three-pass process per folder:

1. **Mechanical pass** (regex): headings `# N — Title` → `# N: Title`; `**Label** —` → `**Label:**` (colon INSIDE bold); list definitions `- Term — def` → `- Term: def`; wikilinks `[[X]] — desc` → `[[X]]: desc` (group chapters as `[[X]] (Ch 5): desc`); quote attributions `> — Name, "Work" (year)` → `> *Name, "Work" (year)*`; empty table cells `| — |` → `| N/A |`.
2. **Classifier pass**: paired dashes (exactly 2 per line) → parentheses; single mid-sentence dash → comma (appositive/gerund/preposition after), semicolon (independent clause or imperative verb after), colon (explanation/list after). Unmatched lines go to a scratch file for manual review.
3. **Manual pass**: read every ambiguous line, write an explicit old→new replacement dict, apply with miss-reporting. Typical ~60-80 lines per folder.

Post-pass normalization: `; Capitalized` → lowercase unless proper noun (keep a PROPER set of author/tech names); `**Label**:` → `**Label:**`; collapse double spaces in prose (skip tables, code, indented lines). En-dashes in ranges (`Ch 12–13`) are CORRECT — keep. Verify: zero `—`, zero `**:`, zero artifacts.

PITFALL: LaTeX lines escape differently (`\tau` in file vs `\\tau` in Python source) — check misses with grep before retrying. Code blocks may contain `# comment` lines that trip naive H1 counts — check `in_code` state.

CODE-BLOCK em-dashes: some folders (Clean Code/Clean Architecture notes) have hundreds of em-dashes inside fenced code as prose comments (`// ❌ Bad — 40+ lines`) or ASCII diagrams. Decide with the user's convention: these ARE prose, so replace too — spaced ` — ` → ` - ` (ASCII art alignment) or `: ` in comments; never touch dashes that are code syntax. Count in_code vs prose separately before declaring done.

CITATIONS: source lines like `*Source: Book — Author*` or `*Clean Code — Robert C. Martin*` need manual rewrites to comma style (`*Clean Code* by Robert C. Martin`), not punctuation swaps; watch for broken italics when substituting (unmatched `*`).

WIKILINK PITFALL: mermaid uses `[[...]]` subroutine-shape syntax (`A --> G[[Label]]`) — protect mermaid blocks before any wikilink replacement. A `[[Book Title]]` link with no target file may be an intentional forward reference (check context, e.g. References section) — leave it and note it. Folder/index links (`[[Folder/|X]]`, `[[Folder/index|X]]`) don't resolve — repoint to the folder's Overview note.

## Mermaid validation & broken-fence repair (2026-09-29 incident)

NEVER trust regex extraction (` ```mermaid\n(.*?)``` `) for validation — it misses unterminated blocks (no closing fence) and mis-pairs fences. Use a fence-aware line walker (open on ```mermaid, close on any next ``` line; track unterminated). Some notes (Microservice sub-vault) have mermaid blocks whose closing ``` was written much later (or never): headings/tables/blockquotes sit INSIDE the diagram and break the render. Fix = insert the missing ``` right after the diagram's real last line (beware `end` lines closing `subgraph` blocks — fence must go AFTER them). FOLDERS 10-12 (2026-09-30) showed a DEEPER pattern: cascading alternation breakage — one missing (or SPURIOUS extra) fence shifts pairing for the whole file (`09_Design_Contract` had 5 missing closers across 27 fences; `10_Syntax` had a spurious ```mermaid that split a code block; `13_07_Vulnerability_Management` had 5 stray fences sitting INSIDE tables). Steps: (1) list ALL fences with positions+info; (2) if count is odd, find the spurious or missing one by content (walk pairs by info tag, not alternation); (3) run an iterative repair: extract blocks with a fence-aware walker, and for every block whose body contains markdown-looking lines (heading/table/blockquote/bold/list/prose sentence), insert a closer at the true diagram end (walk back over blanks), repeat until no block contains markdown — TABLE DETECTION gotcha: the table matcher must be `^\s*\|.*\|` (row has a second pipe), NOT `\|[^\|]*\|>` which only matches arrow cells and missed real tables, leaving swallowed tables unrepaired; (4) re-check both odd-count AND 'mermaid opener followed by another mermaid opener' mispairs; (5) remove stray unpaired fences at EOF when content after them is a table/heading (they're cascade leftovers, not openers) — also when fences sit BETWEEN table rows (consecutive ``` at rows 398/400/402-style), they are stray and must be removed even when the count looks even; (6) render, and if a block still fails with a small line number, the cause may be UNQUOTED PAREN LABELS in node text like `A[X (e.g., Y)]` → quote `A["X (e.g., Y)"]` (parens are shape-start tokens to the parser). ## Fence repair SAFETY RULES (2026-09-30 computing-foundation incident — damaged 8 files)

NEVER remove fence openers based on a content heuristic. The aggressive "block body contains markdown → spurious opener" pass treated bash `# comment` lines (and `6. Presentation`-style numbered prose) as markdown headings and DELETED legitimate code-block openers — 8 files broke (missing closers + orphan openers cascading). Recovery that worked: `git checkout HEAD -- <8 files>` (auto-backup HEAD was clean), then REDO only the reverted files' text work (em/links/theming are deterministic scripts), and repair fences with INSERT-ONLY logic.

VERIFY EVERY fence change against git: `git diff -U0 HEAD -- <folder>` counting `^+``` ` vs `^-``` ` per file. Unbalanced = damage. **Balanced is NOT safe**: +1/−1 can hide a RELOCATED closer (a closer moved from before a prose line to after it = prose swallowed INSIDE a mermaid block → mmdc parse error, but every count/parity check passes). Files with ONLY insertions on odd-at-HEAD files are usually legit author-error fixes.

Full validation chain (all required): (1) semantic fence walk — flagged = tagged line where a closer is expected, or EOF with unclosed block; (2) mermaid openers count == regex-matched blocks count (a mismatch means a block's closer was eaten — typically mermaid-opener-paired-to-mermaid-opener); (3) no markdown (headings/tables/`- [ ]`) inside extracted .mmd bodies; (4) mmdc render all blocks — the only ground truth. Watch: 4-backtick outer fences (````markdown) are VALID for nested README examples — a 3bt-only validator falsely flags them; don't "fix" a correct 4bt structure. Reads must use default universal-newline `open()`; `open(newline="")` breaks ` ```mermaid\n ` regexes (CRLF on disk). Mermaid edge labels contain `|` so naive `\|.*\||` table detectors flag graph lines as tables → false "markdown in block" → bogus repairs. Files on disk are mixed CRLF/LF; git may show a full-file rewrite after edits (EOL normalization) — compare the FENCE SEQUENCE vs HEAD instead of raw diff line counts. Domain symbols: decision-table don't-care entries are dashes, not punctuation — use en-dash `–` to keep the em census at 0 without changing meaning.
